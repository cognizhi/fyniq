# Quality gates

The workbook reached 100% verification of visible numbers against an independent reference
ledger, and FH Cloud keeps that bar (PRD §16). A gate that "blocks merge" really blocks. Fix the
cause; do not skip or weaken the gate.

> **Status:** no code exists yet. P0 builds the harness behind the command contract (§12.8). What
> exists today: `make help`, `make check` (`check-tokens` = the design-token contrast validator,
> `check-config` = release and config validation), `make deps-up` / `deps-down`
> (`deploy/local/compose.yaml`: postgres:18, mailpit, fake-gcs-server) and `make hooks` (installs
> `scripts/hooks/commit-msg`).

## The pyramid

```
  Oracles      reference ledger (independent, Python) · workbook outputs (parity) · hand-pinned statutory figures
  Engine       unit · property · mutation · replay · DB-invariant attacks
  Reports      every visible number verified · every message triggered · snapshots · export round-trip
  System       API contract + breaking changes · authorisation matrix · MCP security · E2E · perf · AI evals
  Platform     local mode with no cloud credentials · image budgets · UI components, a11y, contrast, modes
  Production   nightly ledger and audit-chain verification · canary synthetic transactions
```

## How to write the important kinds

**Differential tests (QA-ENG-02).** Build a scenario (golden fixture or Hypothesis-generated
documents). Post it through the engine against a real PostgreSQL, compute the same scenario in
the oracle, then compare TB by account × period, each subledger and each report figure, to the
cent. On a mismatch, report `account@period engine=X oracle=Y` plus the shrunk scenario. **Never
make the oracle import or call engine code**, and never derive expected values from engine output.

**Property tests (QA-ENG-03).** Use `pgregory.net/rapid` in Go and Hypothesis in the oracle.
Generators produce documents within validation rules **and** just outside them (✖ cases must not
post any leg).

**Every visible number (QA-RPT-01).** Report, KPI, dashboard and export tests compare each
returned figure with an independent expectation through a `verify` helper that **records** what it
compared. A coverage tool lists every figure in API responses that no test compared; the list
must be empty. Expectations come from the inputs and the documented rules (PRD, KPI definitions),
or from the oracle.

**Every message triggered (QA-RPT-02).** Each validation rule has a stable error code (ENG-23).
A fixture must produce each code at least once; the coverage test fails on any code that no
fixture triggers. A new message without a fixture is incomplete.

**DB invariant attacks (QA-ENG-05).** Connect as each application role directly (bypassing the
API) and attempt the forbidden write. Assert the database refuses it with the expected error.
Include the pooled-connection tenant leak.

**Time.** Inject the clock (DEV-05) and freeze dates in every test. Never depend on today.

**AI.** Numbers must come from tools (AI-08). Evals assert exact figures. Replay cassettes are
keyed by model, prompt and tool versions, so a version change forces re-recording in live mode.

## Traceability tags (QA-TRACE-01)

Tag each test with the requirement(s) it proves, on the line above or in the test name:

| Language | Tag |
|---|---|
| Go | `// req: FR-GL-08, INV-03` |
| TypeScript / Playwright | `// req: FR-UX-23` or `@req FR-UX-23` in the test title |
| Python (oracle, evals) | `# req: QA-AI-01` |
| SQL test files | `-- req: INV-02` |

The trace report lists every `M` requirement of the current phase that no test references. The
list must be empty at the phase gate. Do not tag a test with a requirement it does not actually
prove.

## Reading failures

| Symptom | Look at |
|---|---|
| Differential mismatch | **fh-accounting-domain** → "Debugging an imbalance" |
| INV trigger fired in a test | Your code posted something invalid; the database did its job |
| Coverage report lists figures or codes | Add an expectation or a fixture; do not exclude them |
| `oasdiff` breaking change | Make it additive, or plan a new major path (**fh-api-integrations**) |
| QA-LOCAL-01 fails, unit tests pass | A cloud dependency without a local substitute, or an adapter drifted (**fh-local-dev**) |
| Image over budget | A dependency in the runtime stage; **fh-local-dev** §images |
| axe violations / contrast failure | **fh-design-system**; never lower a token's contrast target |
| Mutation survivors | Add the assertion that kills them; record any equivalent mutants in the review |
| Flaky test | Quarantine it **only** with an issue and an owner; fix it within the week. Flaky money tests are bugs. |

## Rules

- `make test` never touches the network beyond package downloads, and never uses cloud credentials.
- Expected values never come from the code under test.
- Every bug fix starts with a failing regression test (**fh-bug-fix**).
- A gate's threshold changes only by a reviewed pull request that also updates PRD §16.

## Definition of done (every change, PRD §16.3)

- [ ] Requirement IDs referenced; acceptance criteria written before code.
- [ ] Tests at the right levels, tagged `req:`; a regression test for every bug.
- [ ] `make test` green locally; coverage reports at 100% where required.
- [ ] Security checklist and threat model updated if money, personal data or permissions are touched.
- [ ] Audit events emitted and verified for every new state change.
- [ ] Works in local mode (`make up` still starts).
