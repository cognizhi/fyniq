## Why

The owner put the company secretary's scheduled agent on the launch path (PRD-001 rev 0.274), and its outputs include
proposals: the tasks the model suggests (`sec.create_task`) and the drafts it writes (`sec.draft_document`,
`sec.draft_reminder`) are tier-1 proposals a person approves (AI-65). The proposal machinery was planned after go-live in
`p1-ai-proposals`. On 15 Nov 2026 the owner decided (rev 0.279) that a minimal slice of it joins the launch, so AI-65
works as written. This change is that slice: the one path by which an AI changes anything, built once and closed by
default, for every task type that follows. The task types themselves come with what they act on: the agent's two with
`p1-scheduled-agents`, the secretary's document with `p1-company-secretary`, the rest with `p1-ai-proposals`.

## What Changes

- **The catalogue as data (§9.6; "Catalogue as versioned, dual-controlled data", "Catalogue entry attributes", "Risk
  tiers and approver roles", "Never in the catalogue"; AI-32; CTL-AI-04)**:
  - one file per task type in `contracts/ai/tasks/`, hash-pinned per release like the read tools: ID, name,
    description, strict input JSON Schema, domain command, tier, limits, approver roles, expiry;
  - the never-list enforced in code, so a never-listed type is refused even if a file adds it;
  - each task type off by default, and enabled per organisation by the Owner under dual control;
  - the catalogue's versioning in the release (platform/release-and-versioning, "AI catalogue").
- **The proposal store (§9.5; "Proposal lifecycle", "Proposal content and payload hash", "Proposal rationale, evidence
  and dry-run impact", "Proposal tier, originator, approvals and execution record")**:
  - an append-only table under FORCE RLS, moving through Draft, Invalid, Pending, Approved, Rejected, Expired,
    Superseded, Executing, Executed, Stale and Failed;
  - each proposal keeps its payload and SHA-256 hash, its items, the AI's rationale and evidence, the dry run's impact
    and base versions, the tier, the originator (AI principal, requester, conversation or run, model, prompt and tool
    versions), its approvals, its execution and its expiry (72 hours).
- **Proposing (AI-P3)**: the AI service's only write. It is an internal operation called with the turn's delegated
  token, which grants no other write. It validates the task type against the catalogue, its enabled flag and its
  schema, then dry-runs the command in a rolled-back transaction to store the impact; a failure is Invalid with a plain
  reason.
- **Approval (AI-P4, AI-P5, AI-06, AI-07, AI-10, AI-14, AI-30, AI-32)**:
  - a proposal is an approval request of the approval engine, whose envelope signs the payload hash;
  - its approval step cannot be removed or automated by any policy or team mode;
  - the review shows a summary generated by platform code from the payload and the impact, the items, the impact, the
    diff and the AI's evidence, with the rationale apart and labelled as AI text;
  - the requester counts as preparer; bulk approval is allowed for tier 1 only;
  - a rejection's reason goes back to the conversation or the run that proposed it;
  - business approval still applies to what it creates.
- **The executor (AI-11, "The executor runs approved proposals as the approving human")**: `cmd/executor` runs the
  approved proposal from its own queue under its own database role. It re-checks the payload hash and the base
  versions (Stale on a change), runs the domain command as the approving human with the AI as originator, in one
  transaction and idempotently by proposal ID, and never bypasses locks, policies or validations.
- **The evals' harness (QA-AI-02)**: proposal suites in `cmd/evals`, judging each scenario's proposal payload against
  its expectation through the real orchestrator. The task types add their scenarios as they arrive.
- **Controls and checks (CTL-AI-02, CTL-AI-03, CTL-AI-04, C.2 #19)**:
  - a nightly reconciliation that every executed proposal has a matching human approval with its payload hash;
  - a policy-engine test that no automatic approval can be configured;
  - the catalogue's dual control and never-list tests;
  - the check for proposals pending more than 48 hours.

## Capabilities

### New Capabilities

None: the requirements are in the main specs already (`ai/proposals`, `ai/task-catalogue`, `ai/evaluation`,
`compliance/ai-and-api-controls`, `controls/platform-checks`, `platform/release-and-versioning`). This change builds
them (`skip_specs: true`).

### Modified Capabilities

None.
