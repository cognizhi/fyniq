| | |
|---|---|
| Document reviewed | `docs/prd/prd-001-finance-hub-cloud-platform.md`, revision 0.1 (initial draft, 2,527 lines) |
| Result | Revision 0.2 of the PRD applies every finding marked **Applied** below |
| Reviewer | Claude Code (Opus 5.5), at the founders' request |
| Review scope | Full read of §1–§21 and Appendices A–I. Extra lenses requested by the founders: complete local test and launch, lean container images, API-friendly and AI-friendly integration, a secure and controlled MCP server, UI review and design with **uipro** (the `ui-ux-pro-max` skill), agent skills and coding instructions, automated versioning |

## 1. Verdict

The PRD is strong where it matters most: the accounting engine, the database-enforced invariants,
the audit trail, the AI proposal layer and the Singapore compliance research are thorough, well
argued and testable. The draft's main weakness is that it describes the **production**
system in detail but says little about how the team **builds, runs, integrates and releases** it:

1. **Local development is promised but not designed.** §12.4 promises "one command starts
   PostgreSQL, the services and the web app", but the architecture depends on services that only
   run in the cloud: Identity Platform, Cloud KMS signing, Bucket Lock, Agent Platform, Model
   Armor, Cloud Scheduler and Secret Manager. There is no plan for running or testing them on a
   laptop or in CI without cloud credentials.
2. **The API comes second.** The public REST API is `S / P2` (FR-INT-01), so the web app would be
   built against a private API that is opened up later. That costs twice and gives integrators a
   second-class surface. The product brief asks for "API-friendly and AI-friendly"; that needs
   the API to be the product surface from P0.
3. **MCP security is a principle, not a design.** The proposal-only rule is right, but the PRD does
   not say who issues OAuth tokens to MCP clients. Identity Platform signs users in to our app; it
   is not an OAuth 2.1 authorisation server for third-party clients. The draft is also silent on
   client registration, consent, token audience, scopes per tool, revocation and the attacks
   specific to MCP.
4. **Container images, versioning and release automation are missing.** "Lean image" has no
   requirement and no budget. Versioning appears only as the name of the `fh-release` skill.
5. **The UI section is good but has gaps.** It conflates the brand accent with the AI accent,
   uses emoji-range symbols as structural icons, misses three WCAG 2.2 / 2.1 criteria that bite a
   keyboard-first app, and leaves a few navigation homes undefined.

None of these change the core architecture. All are fixed in revision 0.2 with new requirement
IDs (no renumbering), three new ADRs (ADR-T3 identity and OAuth, ADR-T4 local mode, ADR-T5
images and releases) and new sections §12.8–§12.10.

## 2. Findings

Severity: **H** = would block a requirement or cause rework if left; **M** = a real gap with a
workaround; **L** = consistency or clarity.

### 2.1 Local development and testing

| # | Sev | Finding | Resolution in rev 0.2 |
|---|---|---|---|
| REV-01 | H | Five production dependencies have no local substitute: Identity Platform (sign-in, TOTP), Cloud KMS (anchor signing, envelope keys), Cloud Storage with Bucket Lock, Claude on Agent Platform with Model Armor, and Cloud Scheduler. Without substitutes, "one command" cannot be met and CI needs cloud credentials. | **Applied.** ADR-T4 "local mode" (§12.8) gives a substitute for every cloud service, behind interfaces the production code also uses: the Firebase Authentication emulator (same API as Identity Platform), a Tink software keyset for KMS, `fake-gcs-server` for Cloud Storage, a recorded-fixture model plus an optional direct Claude API key, and in-process River periodic jobs. Bucket Lock cannot be emulated, so a daily control verifies it in staging. The bootstrap path refuses local adapters when `FH_ENV=production` (DEV-07). |
| REV-02 | H | No requirement that the full test suite runs without cloud access, so local results and CI could drift from each other. | **Applied.** NFR-DEVX-02: `make test` runs every merge gate offline. QA-LOCAL-01: CI boots the full stack with **zero cloud credentials** and runs the smoke, golden and parity suites. |
| REV-03 | M | Toolchain versions are not pinned (Go, Node, pnpm, Python, Typst, OpenTofu), so "works on my machine" problems are likely. | **Applied.** DEV-03: `mise.toml` pins every tool. A dev container is offered for zero-install onboarding. |
| REV-04 | M | Period close, statutory deadlines, CPF age bands and FX revaluation all depend on dates. Without a controllable clock they cannot be tested end to end. | **Applied.** DEV-05: an injectable clock everywhere. A "business date" override exists only in non-production builds. |
| REV-05 | M | The sample company is mentioned in four places (sandbox FR-UX-10, golden tests QA-ENG-07, AI evals QA-AI-01, local dev §12.4) with no single source. | **Applied.** DEV-04: one sample-company generator, used for local seed data, the in-app sandbox, the fixtures and the AI golden set. |
| REV-06 | M | There is no way for a developer to test the MCP server or the AI tools from a real MCP client. | **Applied.** DEV-06: the local stack serves `/mcp` on localhost, so Claude Code or Claude Desktop can be pointed at the sample company. |
| REV-07 | L | Email, malware scanning and external partners (Peppol access point, banks, Stripe) have no local doubles. | **Applied.** In the §12.8 table: Mailpit, a ClamAV profile, and contract mocks generated from the partners' OpenAPI specifications (Prism) plus `stripe-mock`. |

### 2.2 Container images

| # | Sev | Finding | Resolution in rev 0.2 |
|---|---|---|---|
| REV-08 | H | The draft has no image requirements. Defaults (`golang` or `node` bases with a shell and a package manager) produce images of 300 MB to 1 GB. That slows Cloud Run cold starts, enlarges the attack surface and fills scanners with noise. | **Applied.** §12.9 and NFR-IMG-01…05: multi-stage builds; a static Go binary (`CGO_ENABLED=0`, `-trimpath`, `-ldflags "-s -w"`) on `distroless/static:nonroot`; non-root; no shell; read-only root filesystem; base images pinned by digest. **Size budgets enforced in CI:** ≤ 30 MB compressed per Go service, ≤ 90 MB for the render job (Typst and fonts). |
| REV-09 | M | §12.3 lists `proposal-executor` as a River job in the shared worker. The worker also processes untrusted integration input, so it would run under the same service identity as the only component allowed to execute AI proposals. That contradicts §9.3 ("separate service identity"). | **Applied.** §12.3 is corrected: the executor runs in its own worker pool with its own service account and database role. Each service is a **separate binary and image**, so the AI image does not even contain the domain write code. |
| REV-10 | L | The web app needs no image in production (it is static on Cloud Storage and CDN), but local and self-hosted runs need one. | **Applied.** NFR-IMG-04: `nginx-unprivileged` (Alpine) serving the static build, ≤ 25 MB, local and preview environments only. |

### 2.3 API-friendly integration

| # | Sev | Finding | Resolution in rev 0.2 |
|---|---|---|---|
| REV-11 | H | FR-INT-01 (public REST API) is `S / P2`. The web app would therefore be built on a private API first and an external one later. | **Applied.** FR-INT-01 becomes `M / P1` and API-first: the web app uses **only** the public, versioned API (QA-API-03 fails the build on any undocumented endpoint). External third-party access opens in P2 behind the OAuth server (ADR-T3). |
| REV-12 | H | The draft does not cover the conventions an integrator needs: idempotency, pagination, error format, concurrency control, versioning and deprecation, rate-limit signalling. | **Applied.** §8.18.1 API conventions (FR-INT-06…16): `/v1` paths with additive changes; RFC 9457 problem details with stable codes (ties to ENG-23); an `Idempotency-Key` on every POST; ETag and `If-Match` on versioned records; cursor pagination; `RateLimit` headers; RFC 9745 `Deprecation` and RFC 8594 `Sunset` with 6 months' notice; asynchronous operations that return 202 and an operation resource; bulk endpoints with per-item results. |
| REV-13 | M | Webhooks (FR-AUT-04) are `S / P2` but have no specification: signature scheme, retries, replay protection, event catalogue. | **Applied.** FR-INT-12: webhooks follow the **Standard Webhooks** specification (HMAC signature, timestamp, idempotent `webhook-id`, exponential retries for 3 days, a dead-letter view). Events use the CloudEvents envelope, are catalogued in **AsyncAPI 3** under `contracts/events/`, and are delivered from the transactional outbox. |
| REV-14 | M | "Scoped API keys" (FR-INT-02) are listed with OAuth clients, but there is no OAuth authorisation server to issue client tokens (see REV-18). | **Applied.** FR-INT-02 is rewritten: OAuth 2.1 client credentials with `private_key_jwt` for service integrations; personal access tokens only as hashed, expiring, scoped tokens for developers (P2). |
| REV-15 | L | The repository layout differs between §12.2 (`api`, `worker`, `mcp`, `jobs` + `web`) and §12.4 (`apps/`, `services/`, `jobs/`, `contracts/`, …). Feature flags, migrations, search, email and malware scanning have no chosen tool. | **Applied.** §12.4 is the single layout (§12.2 now points to it). §12.2 adds rows for migrations (goose plus the squawk linter), feature flags (OpenFeature with a database-backed provider), global search (PostgreSQL full text and `pg_trgm`), email (a provider interface; Mailpit locally) and malware scanning (ClamAV on Cloud Run). |

### 2.4 AI-friendly integration

| # | Sev | Finding | Resolution in rev 0.2 |
|---|---|---|---|
| REV-16 | H | The draft says nothing about how an external **AI agent** that calls the API is treated. An agent that uses a normal integration credential would bypass the proposal-only rule (AI-P2), which is enforced only for our own orchestrator. | **Applied.** AI-34: every OAuth client has a declared **client class**: `first-party-app`, `integration` or `agent`. **Agents (every MCP client, and any client not explicitly classed) are proposal-only**, whatever scopes they ask for. Integrations get narrow write scopes granted by the Owner with dual control, and their writes still pass the approval policies. |
| REV-17 | M | AI-friendliness depends on machine-readable contracts, but the draft only mentions OpenAPI. | **Applied.** FR-INT-13…16: OpenAPI descriptions and examples written for both humans and models; a **dry-run** mode (`Prefer: return=preview`) on every write command, returning the ledger impact the proposal layer already computes (§9.3); `llms.txt` and an agent guide published with the API docs; a semantic-layer query endpoint (`/v1/metrics:query`) so agents never need SQL; JSON Schema for every resource. A2A (agent-to-agent) agent card: Could, P3. |

### 2.5 MCP server: secure and controlled

| # | Sev | Finding | Resolution in rev 0.2 |
|---|---|---|---|
| REV-18 | H | **No OAuth 2.1 authorisation server.** The MCP authorisation specification needs one, with protected-resource metadata (RFC 9728) and audience-bound tokens (RFC 8707). Identity Platform does not provide consent screens, third-party client registration or resource indicators. | **Applied.** ADR-T3 (§12.2.1): keep Identity Platform for user sign-in; add **Ory Hydra** (Apache-2.0, Go, OpenID-certified) as the OAuth 2.1 authorisation server for MCP clients and integrations, with our API as the login and consent app. Alternatives (embedding `ory/fosite`; Zitadel, now AGPL-3.0) are recorded. [verify Hydra's support for RFC 8707 and RFC 9728 at P0; the API can serve the RFC 9728 document itself if needed] |
| REV-19 | H | The MCP threat model is missing: token passthrough, confused deputy, tool-description injection ("rug pull"), DNS rebinding on streamable HTTP, session hijack, an over-broad first consent. | **Applied.** §9.7 is rewritten into 16 controls (AI-15…17 kept and AI-35…47 added). Highlights: **off by default** per organisation (dual-controlled) and per user; **client allowlist** with dynamic client registration disabled; consent per connection showing scopes and data categories; **scopes map to tools and catalogue task types** (payroll never by default); audience-bound access tokens of at most 1 hour, refresh tokens rotated and revoked on any role change; tokens are never passed through to downstream services; the `Origin` header is validated; tool definitions are static, versioned and hash-pinned; **approvals are never possible over MCP** (only in the web app with a passkey); per-client rate and token budgets and a kill switch; every call is audited with the client ID and version. QA-MCP-01 adds an MCP red-team suite. |
| REV-20 | M | Inconsistent phase: §3.3 says MCP is "P1 (read, first proposals) → P2", while AI-15, FR-INT-03 and §17.2 say P2. | **Applied.** MCP read tools and `propose` for **organisation members using allowlisted first-party clients** (Claude Desktop, Claude Code) move to P1. It is a thin transport over the tool layer §9.3 builds anyway. Third-party clients come in P2. |

### 2.6 Versioning and release automation

| # | Sev | Finding | Resolution in rev 0.2 |
|---|---|---|---|
| REV-21 | H | No versioning scheme for the platform, the API, the database schema, the parameter packs, the AI catalogue and prompts, or the PRD itself. | **Applied.** §12.10 versioning matrix: the platform uses SemVer from **Conventional Commits** via **release-please** (manifest mode); the API version is in the path (`v1`), with `oasdiff` blocking breaking changes; the schema has ordered migrations; packs have their own versions (e.g. `sg-cpf@2027.1`); the catalogue, prompts and tools are versioned per entry; the PRD has a revision number and history table. Images are tagged with the SemVer **and** the git SHA, and deploys use digests. |
| REV-22 | M | §16.3 asks for a CHANGELOG entry per change, written by hand. | **Applied.** release-please generates `CHANGELOG.md` from commit messages. Upgrade notes go in the commit or pull-request body (`BREAKING CHANGE:` footer or an "Upgrade notes" section). Bootstrapped in the repository with this review. |

### 2.7 Other gaps found in the deep read

| # | Sev | Finding | Resolution in rev 0.2 |
|---|---|---|---|
| REV-23 | H | RLS tenant context is "a session variable set by the API". With pooled connections, a session-level `SET` leaks the tenant to the next request. | **Applied.** §11.4: the tenant context is set with `set_config('app.org_id', …, true)` (**transaction-scoped**) at the start of every transaction. Application roles are neither table owners nor `BYPASSRLS`, and every table has `FORCE ROW LEVEL SECURITY`. QA-ENG-05 adds a pooled-connection leak test. |
| REV-24 | M | Real-time collaboration (§3.3, P1) has no mechanism. | **Applied.** FR-UX-19: server-sent events for change notifications (Cloud Run supports streaming responses); ETag-based optimistic concurrency resolves conflicting edits; no CRDT in P1. |
| REV-25 | M | There is no requirement traceability: requirement IDs exist, but nothing checks that tests reference them. | **Applied.** QA-TRACE-01: CI extracts every `M` requirement for the current phase and lists those no test references (`// req: FR-GL-08`). The list must be empty at a phase gate. |
| REV-26 | M | P0 has few functional requirements and no exit criteria. | **Applied.** §17.3 P0 exit criteria: `make dev` and `make test` pass on a clean machine and in CI with no cloud credentials; invariant attack tests are green; the audit chain is anchored in staging; the first release is cut by release-please; the image budgets are met. |
| REV-27 | L | Open questions have no owners or due dates; ADRs live inline with no index. | **Applied.** §20 gets owner and "needed by" columns; §12.0 is an ADR index; new ADRs also go to `docs/adr/` from P0. |
| REV-28 | L | Front-end testing covers E2E and visual regression only. Component tests, accessibility tests per component and a component workbench are missing. | **Applied.** QA-UI-01…03: Vitest and Testing Library; Storybook with the axe add-on; Playwright visual snapshots in both themes, run locally (no SaaS dependency). |

### 2.8 UI review and design (uipro)

Method: `ui-ux-pro-max` design-system generation (several queries; density 8, motion 3, variance
3–4), then targeted domain searches (style, typography, colour, UX, charts, icons and the `shadcn`
stack). uipro's output is used as a **review lens, not as an override**. Its first query
returned a landing-page pattern ("Enterprise Gateway") and an OLED-dark style that rates light
mode "not recommended". Both conflict with an app behind a login that must offer light, dark,
system and high-contrast themes, so they were rejected. What survived is below.

| # | Sev | Finding (uipro rule) | Resolution in rev 0.2 |
|---|---|---|---|
| REV-29 | H | **The brand accent and the AI accent are the same colour.** §7.4 uses the violet-to-teal accent for primary buttons *and* for all AI-originated content "so it is never mistaken for human or posted data". If every primary button is also violet, the colour no longer signals AI. (`color-semantic`, `primary-action`) | **Applied.** Two separate tokens. **Brand/primary** is deep teal: buttons, focus rings, links. **AI** is violet and is used **only** for AI-originated content, always with an "AI" label. The gradient is limited to the Home pulse card and the AI panel header, never on controls (gradients make the contrast of text on controls unpredictable). |
| REV-30 | H | **Status chips use emoji-range symbols as structural icons.** FR-UX-09 says "icons are BMP symbols", but 🔒 (U+1F512) is outside the BMP, and the symbols render differently on every OS. (`no-emoji-icons`, `icon-style-consistent`) | **Applied.** The UI uses one SVG icon set (**Lucide**: shadcn's components ship with it, so mixing in uipro's default Phosphor would break icon consistency) **plus a text label**. The workbook symbols stay in CSV, plain-text email and exports, where they are the user's known vocabulary. |
| REV-31 | H | **Single-key shortcuts (J/K/A/R/E, "G then …", "C I") fail WCAG 2.1.4 Character Key Shortcuts (Level A)** unless users can turn them off or remap them. A one-key "A = approve" is also unsafe for high-risk approvals. | **Applied.** FR-UX-03/06 amended: shortcuts can be turned off and remapped per user; "A" opens the approval confirmation (with step-up where required) and never approves directly; tier-2/3 and FM-1 approvals cannot be bulk-approved by keyboard. |
| REV-32 | M | **Focus can be hidden** by sticky report headers, sticky first columns, side-peek panels and toasts (WCAG 2.2 SC 2.4.11, AA). Fill-down by dragging needs a single-pointer or keyboard alternative (SC 2.5.7). Step-up authentication must allow password managers and paste (SC 3.3.8). (`focus-not-obscured`, `dragging-alternative`, `accessible-authentication`) | **Applied.** NFR-A11Y-03…05. |
| REV-33 | M | **Copying a negative number displayed with U+2212 ("−1,234.56") pastes as text** in Excel and Google Sheets, which breaks the "paste from Excel" round trip that FR-UX-07 relies on. | **Applied.** FR-UX-20: the clipboard and exports always use an ASCII minus and plain decimals. The typographic minus is for display only. Pasted values accept `(1,234.56)`, `S$1,234.56`, `−1,234.56` and the user's locale. |
| REV-34 | M | **Navigation homes are missing** for Contacts, Items, Projects and Employees. The AI assistant and the "AI tasks" page (§9.6) have no place in the information architecture. | **Applied.** §7.1: Contacts is a top-level item (shared by Sales and Purchases); Items sit under Sales; Projects is a feature-switched top-level item (FR-ORG-06); Employees sit under Payroll; the AI assistant is a persistent side panel (⌘J) available on every page, not a nav item; AI tasks sits under Inbox. |
| REV-35 | M | **Live badge counts** (Inbox, Banking) are announced as bare numbers or not at all. (`contextual-live-badge-updates`) | **Applied.** FR-UX-21: a single polite status region announces contextual phrases ("3 approvals waiting"), with atomic updates and no focus change. |
| REV-36 | M | High contrast is "an option" with no definition. The draft says nothing about Windows forced-colours mode. | **Applied.** §7.4: the high-contrast theme follows `prefers-contrast: more` (or a user setting) and meets 7:1 for text. Forced-colours mode is supported with system colours, and focus stays visible. |
| REV-37 | M | **Fonts loaded from a third-party CDN** would add an external request to every page (CSP, privacy and performance). | **Applied.** §7.4: fonts are self-hosted (Inter and JetBrains Mono, SIL OFL) with `font-display: swap` and no third-party font requests. uipro's "Financial Trust" pairing (IBM Plex Sans) is recorded as the alternative if Inter's figures prove too narrow in dense grids. |
| REV-38 | L | Density tokens are undefined ("Comfortable and Compact"). | **Applied.** uipro's data-dense values: 4 px grid; rows 40 px (comfortable) and 32 px (compact), both above the 24 px WCAG target; 56 px header; 240 px sidebar (64 px collapsed); 8–32 px spacing. |
| REV-39 | L | Money values must never be updated optimistically in the UI; the draft is silent. | **Applied.** FR-UX-22: ledger-derived figures render only from server responses; optimistic updates are allowed for non-financial UI state only. |
| REV-40 | H | **Founder request during the review:** the UI needs a **Basic** and an **Expert** mode, so users meet only the features they need and switch with one toggle. The draft has only the narrower Plain / Accountant view (FR-UX-08). (uipro `progressive-disclosure`; the risks to manage are hidden information and lost discoverability) | **Applied.** New §7.8 and FR-UX-23…29: a per-user toggle in the header and command palette; a table of what each mode shows; **presentation only** (permissions, validation and API calls identical; safety information never hidden); an "advanced details" disclosure so nothing on a record is hidden silently; Expert features stay findable from ⌘K in Basic mode; defaults by role; one feature registry with tests (QA-UI-04); usability tests UX-T6/T7. The prototype demonstrates the toggle. |

The design system produced from this review (MASTER rules, OKLCH tokens for light, dark and high
contrast, and the contrast validator) is in `docs/design-system/cognizhi-finance-hub/`. A static
prototype of the shell, Home, Inbox and AI-proposal review is in `docs/design/prototype/`.

2. Confirm the MCP timing: P1 for internal, first-party clients; P2 for third-party clients.
3. release-please opens its release pull requests with the repository's `GITHUB_TOKEN`, so CI

   exists.
