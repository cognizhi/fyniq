# Releasing and versioning

**Nobody edits versions or the changelog by hand** (REL-02). Commit messages carry the release
information, and release-please turns them into versions, a changelog, tags and GitHub releases
(PRD-001 §12.10, ADR-T5). So the most important release skill is **writing the commit message**.

## What exists today

| File | Role |
|---|---|
| `release-please-config.json` | release-please config: `simple` release type, `bump-minor-pre-major: true`, changelog sections, `version-file: VERSION`, `initial-version: 0.1.0` |
| `.release-please-manifest.json` | Current released version (`0.0.0` until the first release). **Without an earlier tag, release-please ignores this value** and uses `initial-version`, so `initial-version: 0.1.0` in the config is what makes the first release 0.1.0; without it the first release would be 1.0.0. After the first tag exists, the manifest drives the bumps. |
| `VERSION` | The version as plain text; equals the manifest (`make check-config` asserts it) |
| `CHANGELOG.md` | Generated by release-please (header only until the first release) |
| `.github/workflows/release-please.yml` | On every push to `main`: opens or updates the release PR; on merge, tags `vX.Y.Z` and publishes a GitHub release. Action pinned by SHA (SEC-28) |
| `.github/workflows/ci.yml` | Pull-request title and commit-message checks (REL-01), `make check` (token contrast, config validity) |
| `scripts/hooks/commit-msg` | The Conventional Commit check; installed locally with `make hooks`; CI uses the same script |
| `scripts/check-commits.sh` | Checks every commit in a range (`make lint-commits RANGE=origin/main..HEAD`) |

## Commit messages (REL-01)

```
<type>(<scope>)<!>: <summary in the imperative, ≤ 100 characters>

<body: what and why, wrapped at 72 characters; requirement IDs, e.g. "Implements FR-GL-04.">

Upgrade notes: <what users, operators or integrators must do>      (optional, REL-03)
BREAKING CHANGE: <what breaks and how to migrate>                  (for "!" commits)
Co-Authored-By: …                                                  (trailers last)
```

| Type | Use for | Version effect |
|---|---|---|
| `feat` | A new capability users, integrators or operators can see | minor |
| `fix` | A defect fix | patch |
| `perf` | Faster, same behaviour | patch |
| `refactor` | Code change with no behaviour change | none (listed) |
| `docs` | Documentation, the PRD, ADRs, skills | none (listed) |
| `test` | Tests only | none (hidden) |
| `build` | Build system, Dockerfiles, images | none (listed) |
| `ci` | Workflows | none (listed) |
| `deps` | Dependency updates | none (listed) |
| `chore` | Housekeeping, including the release PR itself | none (hidden) |
| `revert` | Reverts a commit | per the reverted change |

Add `!` after the type or scope (`feat(api)!:`) **and** a `BREAKING CHANGE:` footer for
anything that breaks a user, an integrator or an operator.

**Scopes** (optional; several allowed, `fix(api,web): …`): `ledger`, `engine`, `api`, `web`,
`ui`, `ai`, `mcp`, `oauth`, `worker`, `executor`, `jobs`, `db`, `infra`, `deploy`, `contracts`,
`oracle`, `packs`, `compliance`, `security`, `design`, `docs`, `prd`, `kb`, `specs`, `skills`, `ci`, `release`,
`deps`. The hook enforces the list; add a scope there and here together.

Pull requests are **squash-merged**, so the PR title becomes the commit subject: CI checks it
with the same script.

Examples:

```
feat(ledger): post FX revaluation with automatic reversal
fix(web): keep the draft when switching to Expert mode
feat(api)!: return money amounts as objects with currency
docs(prd): apply review findings (rev 0.2)
deps(web): update AG Grid to 35.1
```

## SemVer while `0.x` and after go-live

| Phase | `fix`/`perf` | `feat` | Breaking (`!`) |
|---|---|---|---|
| `0.x` (before go-live, P0–P1) | 0.x.**y** | 0.**x**.0 | 0.**x**.0 (`bump-minor-pre-major`) |
| `≥ 1.0.0` (go-live) | x.y.**z** | x.**y**.0 | **x**.0.0 |

Go-live is released as `1.0.0` with a `Release-As: 1.0.0` footer on the commit that completes
the parallel-run sign-off (M5).

## The release flow

1. Commits land on `main` (via reviewed, squash-merged PRs: CTL-CHG-01). Before production, the
   owner's development PRs are approved by `.github/workflows/auto-approve.yml` and auto-merged when
   green (AGENTS.md); the release PR is never auto-approved.
2. release-please opens or updates **one release PR** titled `chore(release): release X.Y.Z`,
   with the bumped `VERSION`, manifest and the new `CHANGELOG.md` section.
3. Review the release PR like any other change (REL-04): read the changelog as a user would;
   check that every breaking change has upgrade notes; check the version bump is right.
4. **Merging the release PR is the release decision.** release-please tags `vX.Y.Z` and
   publishes the GitHub release.
5. (P0) The release job builds the images, tags them `vX.Y.Z` **and** `sha-<git sha>`, signs
   them (cosign), attaches SBOMs and provenance, and deploys to staging **by digest**. Production
   needs the manual approval of §12.4 and shifts traffic gradually with automatic rollback on SLO
   burn.

Note: PRs that release-please opens with the default `GITHUB_TOKEN` do not trigger other
workflows, so release-please runs with an installation token of the organisation's GitHub App
`cognizhi-release-bot` (REL-06, open question 13; 17 Oct 2026). The App ID is the organisation
variable `RELEASE_APP_ID` and its private key the organisation secret `RELEASE_APP_PRIVATE_KEY`.
The token covers this repository only, with contents, issues and pull-requests write, and the
job's own `GITHUB_TOKEN` gets nothing; `TestReleasePleaseRunsWithTheAppToken` (archtest) keeps it
that way.

## Versioning matrix (§12.10)

| What | Scheme | Rule |
|---|---|---|
| Platform | SemVer from Conventional Commits | release-please only |
| Public API | Path major `/v1` + OpenAPI `info.version` = platform version | Additive within a major; `oasdiff` blocks breaking changes (QA-API-02); deprecations get `Deprecation`/`Sunset` headers and ≥ 6 months' notice (FR-INT-06) |
| Events | `fyniq.<object>.<event>.v<N>` | A breaking payload change creates `.v<N+1>`; the old one keeps flowing until its sunset |
| Database schema | goose migrations `db/migrations/NNNNNN_name.sql` | Expand-and-contract; never edit a merged migration |
| Statutory packs | `<pack>@<year>.<n>` with an effective date | Released independently as data (ENG-32/33); see **fyniq-sg-statutory** |
| AI catalogue, prompts, tools | `task_version`, `prompt_version`, `tool_version` | Every change passes the evals and a dual-approved change record (CMP-AI-03); MCP tool hashes re-pinned (AI-40) |
| Images | `vX.Y.Z` + `sha-<git sha>` | Deployed by digest (NFR-IMG-05) |
| Knowledge base | Pages in `kb/` in git; `kb-schema@N` | Compiled, indexed and linted with every source change (`fyniq-knowledge-base`); a schema or compiler-model change means a full recompile and the knowledge evals (QA-AI-06) |
| PRD | Revision `0.N` before go-live, `1.N` after | Revision history row per reviewed change (below) |

## Upgrade notes (REL-03)

Write them in the commit body whenever someone must act. Say exactly what to do and what changes
they will see:

- **Users:** "Bills now require a department when the account requires one; existing drafts
  show ⚠ until completed."
- **Integrators:** "`GET /v1/bills` returns `po_number`; no action needed." / "`amount` is
  deprecated; use `total.amount` before 1 May 2027 (Sunset)."
- **Operators:** "Run the `migrate` job before deploying; the backfill takes about 2 minutes per
  million lines."
- **Numbers that change:** say which reports or balances differ and why (the workbook habit).

## PRD revision convention

`docs/prd/prd-001-fyniq-platform.md` is the **living** spec, not rewritten per
release.

- Bump the revision in the header table and add a row to **Revision history** at the end
  (revision, date, one-line summary).
- New requirements take the **next free ID** in their area and carry `(rev 0.N)`. **Never
  renumber, never delete**: mark a dropped requirement "withdrawn (rev 0.N)".
- Never silently edit a past decision: mark the ADR **superseded** in the §12.0 index and add a
  new ADR (and its `docs/adr/` file from P0).
- Record a review as `docs/prd/reviews/prd-001-review-<date>.md` with finding IDs, and link it.
- (rev 0.10) Update the derived OpenSpec specs and screens in the same commit: `python3 scripts/prdspec.py stale`
  lists the rows to reconvert; then `prdspec.py stamp` and `make check` (**fyniq-openspec**).
- PRD-only changes use `docs(prd): …` (`docs(prd,specs): …` with their specs); they do not bump the platform version.

## Release checklist

1. `git log --oneline origin/main..` reads like a changelog; subjects pass `make lint-commits`.
2. Breaking changes have `!` and a `BREAKING CHANGE:` footer with migration steps.
3. `make check` passes today; from P0, `make ci` (all gates, local mode, images within budget).
4. Contract changes: `oasdiff` clean or a deliberate new major; events versioned.
5. Migrations: expand-and-contract; squawk clean; tested against production-shaped data.
6. Docs synced: user guide, API reference, runbooks, PRD requirement rows if scope changed.
7. The release PR's changelog reviewed; the version bump is right.
8. After merge: the tag and GitHub release exist; (P0) images signed, staging deployed and smoke
   tests green before the production approval.

## Rollback

| Situation | Action |
|---|---|
| Bad deploy, no schema change | Shift traffic back to the previous revision (Cloud Run keeps it); then `revert:` the commit on `main` so the next release is clean |
| Bad deploy with an expand migration | Roll back the service; the expanded schema stays (expand-and-contract makes old code compatible) |
| Bad contract migration | Never roll back by editing a merged migration: write a new forward migration |
| Wrong figures posted | Never edit posted history: correct with approved reversing journals (FR-GL-12); see **fyniq-bug-fix** |
| Wrong statutory pack | Publish a corrected pack version with the same effective date and dual approval; reposting follows ENG-31 |

## Requirements (§12.10)

| ID | Rule |
|---|---|
| REL-01 | Conventional Commits on `main`; PR titles checked |
| REL-02 | release-please manages versions, tags, releases and `CHANGELOG.md` |
| REL-03 | Upgrade notes in commit bodies |
| REL-04 | Release PR reviewed; merging is the release decision; production needs manual approval |
| REL-05 | `/version`, the About dialog and every generated report record version and git SHA |
| REL-06 | GitHub App token for release-please once CI exists |

## Definition of done (a release)

1. Every commit in the release is a Conventional Commit with the right type and scope.
2. The changelog and upgrade notes are something a user can act on.
3. All gates green (`make check` today, `make ci` from P0).
4. Tag `vX.Y.Z`, GitHub release, images by digest (P0) and docs in step.
5. The hand-over says what changed, what users must do, what was verified and what was not.
