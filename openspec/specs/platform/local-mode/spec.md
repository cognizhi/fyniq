# platform/local-mode Specification

## Purpose
How Fyniq runs, tests and launches entirely on a laptop or in CI with no cloud account and no production data: a local adapter behind every cloud dependency, release and local image flavours, local substitutes, the Makefile command contract, one sample-company generator, an injectable clock, and the guards that keep local adapters out of staging and production. Derived from PRD-001 §12.8 (ADR-T4) and §15.

## Requirements

### Requirement: Production and local adapter for every cloud dependency
Every cloud dependency SHALL sit behind a Go interface with two adapters, the production adapter and a local adapter, chosen by configuration (`FYNIQ_ENV=local|ci|dev|staging|production`).

Source: PRD-001 §12.8

#### Scenario: Adapter chosen by configuration
- **WHEN** a service starts with a given `FYNIQ_ENV`
- **THEN** each cloud dependency uses the adapter that the configuration selects

#### Scenario: Same code paths
- **WHEN** a local adapter is used in place of the production adapter
- **THEN** the code above the interface runs the same code paths as in production

### Requirement: Release and local image flavours
Each service image SHALL be built in two flavours from the same commit, Dockerfile, pinned base and hardening: the release flavour (no `local` tag) and the local flavour (`-tags local`).

Source: PRD-001 §12.8

#### Scenario: Only the release flavour reaches staging or production
- **WHEN** an image is deployed to staging or production
- **THEN** it is the release flavour

#### Scenario: Local flavour stays in CI
- **WHEN** a local-flavour image is pushed
- **THEN** it is pushed only to CI's own registry

#### Scenario: Only the local adapter packages differ
- **WHEN** CI builds both flavours of a service
- **THEN** it compares `go list -deps` of the two
- **AND** the only difference permitted between them is the local adapter packages

### Requirement: Local substitutes for data, identity, keys and storage
The local stack (Docker Compose, `deploy/local/compose.yaml`) SHALL substitute the database, sign-in, OAuth, keys, storage and secrets with local equivalents behind the same interfaces.

Source: PRD-001 §12.8

#### Scenario: Database
- **WHEN** the local stack runs in place of Cloud SQL PostgreSQL 18
- **THEN** it uses a `postgres:18` container with the same extensions and password authentication instead of IAM
- **AND** Testcontainers uses the same image for tests

#### Scenario: Sign-in and MFA
- **WHEN** the local stack runs in place of Identity Platform (sign-in, TOTP MFA)
- **THEN** it uses the Firebase Authentication emulator, with the same REST API and token format (its TOTP MFA support is doubtful, so a dev-only OIDC issuer in the `local` build is the expected fallback, confirmed at P0)
- **AND** passkeys (WebAuthn, our own code) work on `localhost`, which browsers treat as a secure context

#### Scenario: OAuth server
- **WHEN** the local stack runs in place of Ory Hydra (ADR-T3)
- **THEN** it uses the same Hydra image

#### Scenario: Keys
- **WHEN** the local stack runs in place of Cloud KMS (anchor signing, envelope keys)
- **THEN** it uses Tink keysets generated by `make setup` into `.data/keys/` (git-ignored), with the same algorithms (ECDSA P-256, AES-256-GCM)
- **AND** key custody differs, by design

#### Scenario: Object storage
- **WHEN** the local stack runs in place of Cloud Storage
- **THEN** it uses fake-gcs-server (GCS JSON API emulator) with the production client library unchanged
- **AND** because Bucket Lock / WORM cannot be emulated, CTL-AUD-03 verifies it daily in staging and production

#### Scenario: Secrets
- **WHEN** the local stack runs in place of Secret Manager
- **THEN** it reads a `.env` generated by `make setup` (git-ignored) through the same `Secrets` interface
- **AND** `.env.example` is committed

### Requirement: Local AI in replay and live mode
The local stack SHALL serve Claude responses in replay mode by default and in live mode only on opt-in, and SHALL substitute Model Armor with a local screening stub.

Source: PRD-001 §12.8

#### Scenario: Replay mode by default
- **WHEN** the AI runs locally without opting in to live mode
- **THEN** it answers from recorded model responses ("cassettes") keyed by prompt, tools and model version, so tests are deterministic

#### Scenario: Live mode on opt-in with synthetic data only
- **WHEN** live mode is switched on with `FYNIQ_AI_LIVE=1`
- **THEN** it calls the Claude API with a developer key, or a developer's own Google Cloud project
- **AND** it uses synthetic sample data only, never real organisation data

#### Scenario: Eval gates run live in CI
- **WHEN** a model or prompt change is proposed
- **THEN** the eval gates (QA-AI-01…03) run in live mode in CI on the sample company before the change

#### Scenario: Local Model Armor stub
- **WHEN** the local stack screens AI input in place of Model Armor
- **THEN** a local screening stub flags the red-team corpus patterns
- **AND** real Model Armor is tested in staging

### Requirement: Local queue and event substitutes
The local stack SHALL run background work with a push dispatcher that has Cloud Tasks' semantics as the local adapter of the queue port (rev 0.23, superseding River), and SHALL use the Google Pub/Sub emulator in place of Pub/Sub (P2).

Source: PRD-001 §12.8

#### Scenario: A push dispatcher in place of Cloud Tasks and Cloud Scheduler
- **WHEN** background work runs locally in place of Cloud Tasks and Cloud Scheduler → Cloud Run jobs
- **THEN** after commit the push dispatcher POSTs each outbox row's task to its worker class's HTTP handler with that class's token, honouring task names and deadlines, retrying, and re-dispatching under a new name
- **AND** the local tick calls the same handlers, so one schedule definition, the same HTTP path, token check and leases serve both
- **AND** only Cloud Tasks' own retry settings and quotas are left to staging

#### Scenario: River for self-hosted installations
- **WHEN** a self-hosted installation needs a queue without Cloud Tasks
- **THEN** River remains the option, behind the same queue port (River as the local adapter is superseded, rev 0.23)

#### Scenario: Pub/Sub emulator
- **WHEN** Pub/Sub (P2) is used locally
- **THEN** the Google Pub/Sub emulator is used with the same client library

### Requirement: Local edge, email, messaging and partner substitutes
The local stack SHALL substitute the load balancer, email, chat messages, malware scanning, partner APIs and observability with local equivalents.

Source: PRD-001 §12.8

#### Scenario: One local origin
- **WHEN** the local stack runs in place of the load balancer, Cloud Armor and CDN
- **THEN** Caddy serves one origin for the web app, `/api`, `/ai`, `/mcp` and `/oauth2`, with the same cookie and CSP behaviour
- **AND** WAF rules are tested in staging

#### Scenario: Email to Mailpit
- **WHEN** the local stack sends email
- **THEN** it goes to Mailpit (inbox UI at `localhost:8025`) and templates and links are checked end to end

#### Scenario: Slack and Zoho Cliq to a local message sink
- **WHEN** the local stack posts to Slack or Zoho Cliq
- **THEN** a local message sink (`/dev/messages`) shows what would be posted, with the same payloads
- **AND** routing and content level are checked end to end

#### Scenario: Malware scanning stub
- **WHEN** the local stack scans an upload
- **THEN** a stub rejects the EICAR test file
- **AND** a `clamav` profile runs the real engine

#### Scenario: Partner mocks
- **WHEN** the local stack calls a Peppol access point, a bank API or the payment provider
- **THEN** Prism mock servers built from the partners' OpenAPI documents in `contracts/partners/`, and `stripe-mock`, answer at contract level
- **AND** partner sandboxes are used in staging

#### Scenario: Observability profile
- **WHEN** the `obs` profile is started
- **THEN** an OpenTelemetry Collector and Jaeger receive the same OTel instrumentation as production

### Requirement: Makefile command contract
The Makefile SHALL be the single entry point for running, testing and launching Fyniq locally, and CI SHALL call the same targets.

Source: PRD-001 §12.8

#### Scenario: make setup
- **WHEN** `make setup` runs
- **THEN** it installs the pinned toolchain (`mise`) and creates `.env`, the local keys and the Hydra clients for the first-party apps

#### Scenario: make dev
- **WHEN** `make dev` runs
- **THEN** the full stack starts with hot reload (Go with `air`, Vite HMR) and the sample company loaded
- **AND** it prints the URLs, and any sample user can sign in

#### Scenario: make up and make down
- **WHEN** `make up` runs
- **THEN** the stack runs from the local flavour of the release images (same Dockerfile, base and hardening, plus the local adapters, ADR-T4), not dev builds
- **AND** `make down` stops it

#### Scenario: Release flavour proven elsewhere
- **WHEN** the release flavour itself must be proven
- **THEN** it is proven by `make images` (budgets, QA-IMG-01 symbol check), the start-up refusal test (CTL-CHG-09) and the staging smoke suite

#### Scenario: make seed and make reset
- **WHEN** `make seed` or `make reset` runs
- **THEN** `make seed` reloads the sample company and `make reset` wipes local data

#### Scenario: make test
- **WHEN** `make test` runs
- **THEN** every merge gate runs offline: unit, property, database invariant attacks (Testcontainers), differential tests against the oracle, contract tests, the authorisation matrix, and front-end unit and accessibility tests

#### Scenario: make test-e2e and make evals
- **WHEN** `make test-e2e` or `make evals` runs
- **THEN** `make test-e2e` runs the Playwright journeys (QA-E2E-01) against `make up`
- **AND** `make evals` runs the AI golden, proposal and red-team suites, in replay by default and live with `FYNIQ_AI_LIVE=1`

#### Scenario: make images, make ci and make help
- **WHEN** `make images`, `make ci` or `make help` runs
- **THEN** `make images` builds every image, enforces the size budgets and scans them (§12.9)
- **AND** `make ci` runs exactly what CI runs, in the same order
- **AND** `make help` lists the targets

### Requirement: DEV-01 Full stack from a clean machine
`make setup && make dev` SHALL bring up the full stack (web, API, AI, MCP, OAuth, worker, executor, database, local substitutes) on a clean machine with Docker and `mise` in ≤ 10 minutes, and ≤ 60 seconds on later runs.

Source: PRD-001 §12.8 · Priority M · Phase P0

#### Scenario: First run on a clean machine
- **GIVEN** a clean machine with Docker and `mise`
- **WHEN** `make setup && make dev` runs for the first time
- **THEN** web, API, AI, MCP, OAuth, worker, executor, database and the local substitutes are up in ≤ 10 minutes

#### Scenario: Later runs
- **GIVEN** the stack has been set up before on the machine
- **WHEN** `make dev` runs again
- **THEN** the full stack is up in ≤ 60 seconds

### Requirement: DEV-02 No cloud credentials or production data needed
No cloud credentials, cloud project or production data SHALL be needed for `make dev`, `make test`, `make test-e2e` or `make evals` (replay mode).

Source: PRD-001 §12.8 · Priority M · Phase P0

#### Scenario: Commands run without a cloud identity
- **GIVEN** a machine with no cloud credentials, no cloud project and no production data
- **WHEN** `make dev`, `make test`, `make test-e2e` or `make evals` (replay mode) runs
- **THEN** it completes without needing any of them

#### Scenario: G4-079 Clean CI runner runs make up
- **GIVEN** a clean CI runner with no cloud identity
- **WHEN** it runs `make up`
- **THEN** the stack boots from local-flavour images built from the same commit
- **AND** the smoke, golden and parity suites pass

### Requirement: DEV-03 Pinned toolchain and dev container
Toolchain versions (Go, Node, pnpm, Python, Typst, OpenTofu, golangci-lint, …) SHALL be pinned in `mise.toml`, and a dev container (`.devcontainer/`) SHALL give the same environment with zero installs.

Source: PRD-001 §12.8 · Priority M · Phase P0

#### Scenario: Toolchain pinned in mise.toml
- **WHEN** a developer installs the toolchain
- **THEN** the versions of Go, Node, pnpm, Python, Typst, OpenTofu, golangci-lint and the other tools come from `mise.toml`

#### Scenario: Dev container
- **WHEN** a developer opens the repository in the dev container (`.devcontainer/`)
- **THEN** they get the same environment with zero installs

### Requirement: DEV-04 One sample-company generator
One sample-company generator SHALL feed the local seed data, the in-app sandbox (FR-UX-10, FR-INT-18), the golden fixtures (QA-ENG-07) and the AI golden set (QA-AI-01).

Source: PRD-001 §12.8 · Priority M · Phase P0

#### Scenario: All sample data from one generator
- **WHEN** local seed data, the in-app sandbox, the golden fixtures or the AI golden set are produced
- **THEN** each is produced by the same sample-company generator

### Requirement: DEV-05 Injectable clock
Every component SHALL read time through a clock interface that tests can freeze, and non-production builds SHALL offer a "business date" override.

Source: PRD-001 §12.8 · Priority M · Phase P0

#### Scenario: Tests freeze the clock
- **WHEN** a test runs
- **THEN** it freezes the clock that every component reads time through

#### Scenario: Business date override
- **GIVEN** a non-production build
- **WHEN** the business date is overridden
- **THEN** period close, statutory deadlines, CPF age bands and FX revaluation can be exercised on that date

### Requirement: DEV-06 Local MCP endpoint
The local stack SHALL serve `/mcp`, so Claude Code or Claude Desktop can connect to the sample company with the same OAuth flow as production (§9.7).

Source: PRD-001 §12.8 · Priority S · Phase P1

#### Scenario: Claude connects to the local stack
- **WHEN** Claude Code or Claude Desktop connects to the local `/mcp`
- **THEN** it goes through the same OAuth flow as production (§9.7)
- **AND** it reaches the sample company

### Requirement: DEV-07 Local adapters only in local builds
Local adapters SHALL exist only in builds tagged `local`, and the production binary SHALL refuse to start with any local adapter or with `FYNIQ_ENV` other than `staging` / `production`.

Source: PRD-001 §12.8 · Priority M · Phase P0

#### Scenario: Refuses a local adapter
- **WHEN** the production binary starts with a local adapter configured
- **THEN** it refuses to start

#### Scenario: Refuses a non-production environment
- **WHEN** the production binary starts with `FYNIQ_ENV` other than `staging` or `production`
- **THEN** it refuses to start

#### Scenario: No local adapter symbols in production images
- **WHEN** CI builds the production images
- **THEN** it asserts that they contain no local adapter symbols

#### Scenario: Only release-flavour digests deployed
- **WHEN** the deploy pipeline deploys to staging or production
- **THEN** it admits only release-flavour digests

#### Scenario: G4-080 Local image or local environment offered to staging
- **WHEN** a local-flavour image, or a release image with `FYNIQ_ENV=local`, is offered to staging
- **THEN** the deploy is rejected (digest not release flavour) or the service refuses to start
- **AND** nothing reaches traffic

### Requirement: DEV-08 Synthetic data only outside production
Seeded local and preview data SHALL be synthetic, and production data SHALL never be copied to developer machines or non-production projects (CTL-CHG-05).

Source: PRD-001 §12.8 · Priority M · Phase P0

#### Scenario: Seeded data is synthetic
- **WHEN** a local or preview environment is seeded
- **THEN** the data is synthetic

#### Scenario: Production data stays in production
- **WHEN** data is copied to a developer machine or a non-production project
- **THEN** it is never production data (CTL-CHG-05)

### Requirement: NFR-MAINT-01 Everything as code, one command each
Everything SHALL be as code, with one command to run the full stack locally and one command to run all tests.

Source: PRD-001 §15 · Priority M · Phase P0

#### Scenario: Everything as code
- **WHEN** any part of the platform is set up or changed
- **THEN** it is defined as code in the repository

#### Scenario: One command for the stack and one for the tests
- **WHEN** a developer runs the full stack locally, or runs all tests
- **THEN** each takes one command

### Requirement: NFR-DEVX-01 Local launch time
`make setup && make dev` on a clean machine SHALL bring up the full stack with the sample company (DEV-01) in ≤ 10 min on the first run and ≤ 60 s on later runs.

Source: PRD-001 §15 · Priority M · Phase P0

#### Scenario: First run measured on a clean machine
- **GIVEN** a clean machine
- **WHEN** `make setup && make dev` runs for the first time
- **THEN** the full stack with the sample company is up in ≤ 10 min

#### Scenario: Later runs measured
- **WHEN** `make dev` runs again on the same machine
- **THEN** the full stack with the sample company is up in ≤ 60 s

### Requirement: NFR-DEVX-02 Local test time
`make test` SHALL run every merge gate offline, with no cloud credentials (DEV-02), in ≤ 10 min on a developer laptop.

Source: PRD-001 §15 · Priority M · Phase P0

#### Scenario: Offline merge gates on a laptop
- **GIVEN** a developer laptop with no network access to the cloud and no cloud credentials
- **WHEN** `make test` runs
- **THEN** every merge gate runs
- **AND** the run finishes in ≤ 10 min

### Requirement: NFR-DEVX-03 Feedback loop
A Go change SHALL restart its service, and a web change SHALL be applied by hot module reload, within ≤ 3 s.

Source: PRD-001 §15 · Priority M · Phase P0

#### Scenario: Go change
- **GIVEN** `make dev` is running
- **WHEN** a Go source file is saved
- **THEN** the affected service is restarted within ≤ 3 s

#### Scenario: Web change
- **GIVEN** `make dev` is running
- **WHEN** a web source file is saved
- **THEN** the change is applied by hot module reload within ≤ 3 s
